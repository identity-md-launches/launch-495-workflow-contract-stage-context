# Launch review handoff

This is a source-builder handoff, not an independent review or permission to deploy. The source and ABI are reviewable now; a separate contributor must inspect accepted source together with the generated manifest and its concrete arguments. Policy signatures, source publication and attestation linkage are service responsibilities.

1. **Release-scope conflict:** the approved game brief says no new token, pool or liquidity. The mandatory `evm_project` launch requirements require a separate fixed-supply LaunchToken and protocol liquidity. The repository supplies the mandatory PJACK token, keeps it out of jackpot accounting, and does not claim these release requirements are equivalent. The launch review must resolve the source/manifest/policy conflict; substituting PJACK for existing ICE or IMD is incorrect.
2. **Constructor representation:** the brief names a manager, two PoolKey tuples and wrapper. The factory supports static scalar constructor arguments. PepeJackpot instead takes `(manager, ice, iceHook, imd, wrapper)` and derives the exact specified native-currency keys, fees and tick spacing. Review the exported ABI and all five concrete mainnet addresses. There is no privileged `$owner` and no initialization transaction. Address checks intentionally avoid external reads in the constructor so offline construction succeeds; release services must validate dependency identities and state.
3. **External ownership persists:** although PepeJackpot has no admin, the existing LaunchpadHook can change its creator/burn fee rates and the pool backing ICE's curve. The wrapper/coordinator governs VRF availability and pricing. These are required existing dependencies, not privileges secretly added to the jackpot.
4. **Custody and asynchronous outcomes:** an unanswered or failed VRF callback expires unpaid after 24 hours, including its ticket contribution and spent oracle fee. Winners use the pot at delivery time; callback ordering matters. Failed payouts remain reserved, with no admin recovery route. Confirm these semantics with the frontend and reviewers.
5. **Fixed operational choices:** callback gas is 500,000 (the draw, its storage writes and a bounded 100,000-gas transfer attempt; no manager unlock), request confirmations are three, and one word is requested. No setter can adapt them after deployment. Fork testing exercises deployed dependency code but does not verify a live oracle proof or establish sufficient confirmations for every possible pot value.
6. **Fulfilment is lock-free by design (revision after independent review):** the first accepted version routed `rawFulfillRandomWords` through `PoolManager.unlock` under the contract's own reentrancy guard. Because the coordinator accepts a valid proof from any sender and the wrapper swallows a consumer revert without retry, a third party holding either lock at delivery time could void a winning ticket. The revision calls `_draw` directly from the authenticated callback and gates `deliverPayout` on the self-call sender alone. `claim()` still runs inside an unlock; only the claimant's own transaction can be affected there, and it retries freely.
7. **Codeless dependencies and chain identity are enforced only by the policy:** the constructor cannot read dependency code without failing the offline launch floor. The README's deployment section lists the admission evidence the deployer must produce (chain ID 1, non-empty code at all five addresses, 18 decimals, the hook's PoolManager, Cancun acceptance). A wrong chain or wrong address deploys a permanently unusable application with no repair path.
8. **Per-trade eligibility and the 90% jackpot are the brief's economics:** every eligible ticket, whatever its fee, gets the same 1/100 chance at 90% of the pot, so fees do not grow the pot in expectation and splitting a trade into minimum tickets multiplies expected payout. The README documents the expected-value table. This is a requester scope decision to confirm before deployment, not a source defect.

See `README.md`, dependency provenance, and the fork rehearsal report for deployment parameters, testing boundaries and operational responsibilities. No independent reviewer approval, manifest validation or live deployment is asserted by this repository.
